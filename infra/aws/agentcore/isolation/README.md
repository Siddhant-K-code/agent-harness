# Command isolation boundary

Every `agentcore.Client` command enters the image-owned `harness-guard` executable. The command text is one quoted argument; neither profile nor text is concatenated as an outer shell program. `work` and `verify` are the only accepted profiles. There is no raw-command fallback.

The guard runs as an ordinary non-root UID. It closes inherited descriptors above stderr, rejects unexpected standard-stream types, sets `no_new_privs`, installs a seccomp allowlist, clears the environment, changes to `/workspace`, then executes Bash. Failed policy setup exits 125 before the command executes. Unprivileged seccomp and descriptor-closing support are mandatory; unavailable policy setup has no unrestricted fallback. The C launcher is single-threaded during setup; restrictions are inherited across exec and child creation.

- Both profiles deny socket creation, network operations, io_uring, descriptor theft, ptrace/process-memory access, cross-process signalling, and new namespaces. This includes localhost and Unix sockets. The guard also blocks device ioctls except FIOCLEX (close-on-exec, needed by musl) and FIONBIO (nonblocking mode, needed by Node pipe-backed stdio). These operations neither create sockets nor grant file write access.
- Work commands can write wherever the non-root guest UID has filesystem permission. The verifier denies filesystem writes globally, including `/tmp`; it cannot write, truncate, rename, remove, create, or change metadata on files. Only read-only open flags are allowed, and file mutation syscalls are absent from the allowlist. Writable inherited file descriptors are rejected or closed. `openat2` is unavailable because classic seccomp cannot inspect its pointer-encoded flags; callers can use checked `open`/`openat` instead.
- The verifier runs in a fresh AgentCore session after a trusted candidate transfer. It receives the independent verifier through the command payload, after the filesystem restrictions are installed. A nested `work` launcher cannot relax an inherited verifier policy.

`checks.py` attempts TCP/UDP/IPv6/Unix sockets, io_uring, a child-process escape, direct writes/truncation, shared writable mappings, creation flags, symlink and proc-fd aliases, hard links, rename/unlink, metadata changes, scratch writes, and a nested launcher. `test_guard.py` adds positive controls in an unrestricted container and verifies inherited socket closure and environment clearing. CI builds and executes the real image; the AWS workflow repeats the checks against the actual runtime. A passing local check does not establish kernel support in AWS.

This is a command-process boundary, not a claim that the entire AgentCore microVM has disabled networking. Its trusted HTTP service still uses the platform network. The guest role remains minimally scoped and is not considered secret from guest code. Unix-socket tools, network-dependent builds, signalling utilities, and some debuggers are intentionally unsupported by this initial strict profile. Filesystem isolation alone does not make an in-process language verifier immune to candidate monkeypatching or prove arbitrary code correct. Filesystem capacity remains unbounded; kernel vulnerabilities, side channels, and arbitrary workload compatibility are outside this evidence. The [full AWS adapter](../../../../docs/aws-harness.md) adds artifact handoff, controller ownership and whole-runtime reconciliation; its separate live acceptance also passed.

The initial Landlock implementation refused execution on the real AWS runtime because the required ABI was unavailable. The final verifier profile uses a stricter global write denial through seccomp and does not depend on Landlock.

Reference: [seccomp](https://man7.org/linux/man-pages/man2/seccomp.2.html). The checked-in implementation uses the system's libseccomp; its compiled binary is identified by the immutable runtime image digest.
